# Unity 에이전트 협업

[공통 협업 절차](../agent-collaboration.md)를 Unity 작업에 적용할 때 읽는다. `core.md`의 참조 규칙과 에셋 변경·검증 규칙, [Feature Composition](composition.md)의 책임 경계를 그대로 따른다.

## 역할과 접점

- 설계 담당은 기존 Feature·Common을 확인해 재활용·추가 범위를 정하고, Feature별 책임과 `Property`·`Command`·`Event` 계약, 파일 담당을 설계한다. 접점의 단위·유효 시점·이벤트 순서 등 연결에 필요한 조건도 정한다.
- Feature 개발 담당들은 합의된 접점에 따라 독립적으로 구현한다. 다른 Feature를 직접 참조하지 않으며, 구현별 동작과 접점을 검증한다.
- Common 개발 담당은 여러 사용처에 필요한 공용 요소가 있을 때만 둔다. Feature나 Composition의 책임을 Common으로 옮기거나 추측에 따른 인터페이스·추상화를 추가하지 않는다.
- Composition 담당은 설계 때 접점의 연결 가능성, 초기화·구독·해제 순서와 소유권을 검토한다. 관련 Feature·Common 구현이 준비되면 Root·Sub-Composition·Adapter를 통해 연결하고 통합 검증한다. 연결 편의를 위해 Feature 접점을 임의로 바꾸지 않는다.

역할 구분을 위해 클래스나 Composition을 추가하지 않는다. 작은 작업은 메인이 여러 역할을 함께 맡는다.

## Editor와 공유 환경

- Unity Editor와 mcp-for-unity 조작은 메인만 수행한다. Scene·Prefab 연결이 필요한 담당자는 대상, 필요한 참조·구성, 확인할 동작을 메인에게 인계한다.
- `.unity`, `.prefab`, `.meta`를 직접 수정하지 않는다. 에셋 이동·이름 변경도 메인이 해당 규칙에 따라 수행한다.
- 스크립트 파일 편집은 담당별로 나눌 수 있지만, Unity 컴파일·Console 확인·Play 모드 검증은 공유 환경을 사용한다. 메인은 관련 편집 완료 시점을 모아 검증을 직렬로 조율한다. 검증 중에는 대상 파일의 편집을 멈추고, 추가 변경이 발생하면 해당 변경이 포함된 상태로 다시 확인한다.
- 컴파일 오류가 다른 담당의 미완성 변경에서 발생하면 원인과 담당을 공유하고 관련 작업을 조율한다. 오류를 숨기기 위해 합의된 계약이나 동작 경로를 바꾸지 않는다.

## 검증 범위

개발 담당은 가능한 범위에서 자신이 맡은 구현의 동작과 접점 계약을 확인하고 결과를 인계한다. Unity 컴파일 확인이 필요하면 메인에게 요청하며, 확인 전에는 검증 완료로 표시하지 않는다.

메인은 편집 완료 후 `core.md`에 따라 refresh, 컴파일 완료 대기, Console 오류 확인을 수행한다. Composition 연결 후에는 가능한 범위에서 Play 모드로 실제 Feature 간 전달, 초기화·종료, 이벤트 구독·해제를 확인한다. 실기기 확인 등 수행하지 못한 범위는 최종 보고에 명시한다.
